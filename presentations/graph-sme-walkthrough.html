09 Decision fork

Prefer lakehouse edges first; add a graph engine when concurrency and Cypher/SPARQL expertise demand it

Prefer on Databricks

Edge tables · Genie · SPARQL→SQL

  • Agent context and knowledge exploration
  • Multi-hop analysis with recursive SQL or hop views
  • Algorithms via NetworkX, SparkGraph, or cuGraph → Delta
  • Delta remains system of record under Unity Catalog
When a dedicated engine fits

Partner DB or OntoBricks

  • Existing Cypher/SPARQL applications on staff
  • Sub-second OLTP-style traversal at high concurrency
  • Formal OWL reasoning / SHACL validation required
  • Still sync outward from governed Delta edges

12 Operating rule

Standardize on the edge contract early; climb only with demonstrated need

✓
Evaluate managed ontology firstGenie Ontology + Glossary + Metric Views + Relationships before custom builds.
✓
Land gold_triplets onceGenie, explorers, algorithms, and agents all consume the same Delta contract.
✓
Benchmark before climbingProve edge+Genie or SPARQL→SQL short against real queries.
✓
Precompute heavy workBatch algorithms and hop closures to Delta; serve cheap lookups.
✓
Keep Delta as system of recordPartner engines sync outward; governance stays in Unity Catalog.
✓
Treat entity resolution as first-classSAME_AS edges are usually the hardest part of a real knowledge graph.

13 Discussion

Map your use case to a starting rung

The proposal

Begin at the lowest rung that can answer your benchmark queries. Expand only when those queries fail for a concrete, demonstrated reason.

What queries must work on day one — joins, multi-hop, algorithms, or formal reasoning?
Have you tried Genie Ontology / Glossary / Metric Views against those queries?
Do you need GraphRAG for enumeration and composition, or for governed agent memory?
Who owns ontology curation — and do you have Cypher/SPARQL expertise on staff?
